# GH200 vLLM 0.29 stack trial

Candidate only; no production promotion or throughput claim.

## Inputs

- Base: main 9957b377 plus replica telemetry b30237c5f.
- vLLM 0.29.0 official ARM64 CUDA wheel; release source 98dff2a81d747d1dba01a47f939f48c3526d4206.
- Torch 2.13.0+cu130, torchvision 0.28.0+cu130, Triton 3.7.1.
- vLLM worker: FlashInfer 0.6.18, TileLang 0.1.12, CUTLASS DSL 4.6.2.
- TE 2.18 and NCCL 2.30.7 retained. Bridge/MCore pins unchanged.
- MCore FlashAttention is built from source against the new Torch ABI.
- Only the Apertus actor profile (Megatron plus vLLM) is in scope. Other optional backends are not qualified by this trial.

## Compatibility

The Apertus loader patch accepts both multiline and single-line AutoWeightsLoader calls. Legacy xIELU constants are validated and excluded from refit; mismatches still fail. Shared protocol imports support the old and new vLLM layouts. The Apertus tool parser accepts request tools, correcting a preexisting constructor mismatch also present against vLLM 0.26.

The old TCPStore and MessageQueue patch anchors are absent in 0.29 because upstream now allocates and holds sockets (TCPStore port=0 with a retained store, and ZMQ bind port=0). Existing patch functions warn and skip; no new synchronization patch is introduced here.

## Validation and launch gates

- 34 build/assembly/manifest CPU tests and 18 loader/chat/parser/token-limit tests pass.
- New loader and parser regressions reproduced before fixes. Ruff, shell syntax, diff whitespace, and offline lock check pass.
- Independent review checked exact 0.29 source; its parser finding was fixed and regression-tested.
- Build hermetic dependencies in one allocation, release in another, and assemble SquashFS separately. Keep the production image available.
- Candidate qualification must import native extensions and execute CUDA before repeated 70B refit/training.
- Compare identical 70B BF16 checkpoints and DAPO inputs, thinking on, 12,288 new tokens in a 16,384 context, GBS768, MB1, trainer TP2/PP4 on 24 nodes, rollout TP4/PP1 on 16 nodes, 16 responses per prompt, staleness1. Retain optimizer checkpoints.
- Record startup separately from steady-state steps, emitted tokens, per-replica load, trainer waiting, refit, peak memory, actual kernel selection, and logprob parity. Same seeds do not guarantee identical sampled text across engines; normalize throughput by generated tokens and report realized lengths.

Actual jobs, images and evidence are recorded in the campaign session ledger. GPU compilation, refit correctness and throughput remain pending.
